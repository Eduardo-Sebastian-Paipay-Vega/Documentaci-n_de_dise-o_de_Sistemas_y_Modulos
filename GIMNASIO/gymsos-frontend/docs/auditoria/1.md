FASE 4 — EVALUACIÓN DEL MODELO RBAC
Estado actual: RBAC híbrido con inconsistencia dual
El sistema tiene dos capas de roles que no están sincronizadas:

Capa 1 — Legado (gym.usuarios.rol): string enum {gerente, recepcionista, entrenador, nutricionista, miembro, cliente, admin}. Controla enrutamiento de dashboards y algunas políticas RLS antiguas en el schema gym.

Capa 2 — RBAC moderno (public.user_roles): roles por tenant con jerarquía y permisos granulares. Controla acceso a funcionalidades específicas via fn_has_permission().

¿Conviene mantener roles rígidos o evolucionar a permisos?
Veredicto: RBAC + permisos granulares (modelo actual) es el correcto, pero necesita unificación.

Opción	Ventajas	Desventajas	Apto para GymSOS
RBAC puro (solo string rol)	Simple, fácil de entender	Inflexible, no escala, no permite customización	❌ No
Solo permisos (sin roles)	Máxima granularidad	Gestión compleja, difícil de explicar a usuarios no técnicos	❌ No
RBAC + permisos granulares	Balance poder/usabilidad, roles como agrupadores, permisos para excepciones	Requiere UX cuidadoso para no confundir	✅ Sí
Modelo híbrido con jerarquía	Herencia de permisos, override por usuario	Complejidad alta de implementación	⚠️ Futuro
Recomendación arquitectónica: Mantener el modelo actual (RBAC con roles como contenedores de permisos) pero eliminar gradualmente la dependencia del string gym.usuarios.rol para la lógica de negocio. Ese campo debe quedar solo para el enrutamiento inicial de dashboard (UX), no para autorización real.

FASE 5 — AUDITORÍA DEL MÓDULO DE CÓDIGOS
¿Qué problema resuelve?
El módulo de códigos resuelve el problema de incorporación controlada de personal sin requerir intervención manual del administrador en tiempo real. Sin él, añadir un cajero nuevo requeriría que el admin creara la cuenta manualmente en Supabase. Con él, el admin genera un código con permisos predefinidos y el trabajador se autoregistra.

Valor de monetización
Los códigos de invitación permiten controlar el número de trabajadores activos por plan de suscripción (campo max_licenses en public.tenants). Un plan "básico" puede limitar a 5 licencias de staff, mientras "enterprise" es ilimitado. Actualmente esta validación no está implementada en fn_create_staff_code, pero la infraestructura (max_licenses en tenants) existe.

Clasificados por prioridad
CRÍTICOS (bloquean operación o representan riesgo de seguridad)

ID	Vacío	Riesgo	Descripción
GAP-001	Doble sistema de roles no sincronizado	Seguridad / Consistencia	gym.usuarios.rol (string) y public.user_roles (RBAC) existen en paralelo. El middleware de rutas usa el string antiguo; la autorización usa RBAC. Un "cajero" no tiene ruta de dashboard.
GAP-002	Rol "Cajero" y "Supervisor" sin ruta de dashboard	UX / Funcional	Existen en RBAC pero no en roles.ts. Si un usuario tiene rol Cajero/Supervisor en RBAC, el sistema lo enruta como miembro (fallback) o rompe la sesión.
GAP-003	Sin UI para revocar roles de staff	Seguridad operativa	Un trabajador que se desvincula del gym conserva sus permisos indefinidamente. No hay UI para revocar. fn_revoke_code existe pero no tiene pantalla.
GAP-004	max_licenses de tenants no validado en fn_create_staff_code	Monetización / Seguridad	Un gym en plan básico puede crear códigos ilimitados. La columna max_licenses existe en public.tenants pero no se valida.

ID	Vacío	Riesgo	Descripción

GAP-006	Sin listado de staff activo con sus roles RBAC	Gestión operativa	No hay pantalla que muestre: "estos son mis trabajadores, estos son sus permisos actuales".
GAP-007	user_roles.expires_at sin procesamiento	Seguridad	La columna existe y fn_has_permission la verifica, pero no hay job que cambie el status cuando expira. Un rol expirado simplemente deja de funcionar (correcto) pero sin feedback visible al usuario.
GAP-008	Sin módulo de configuración funcional	Operativo	La ruta /dashboard/gerente/configuracion existe en sidebar pero la página no tiene contenido funcional real.

GAP-010	Sin CRUD de roles personalizados	Funcional	Los 7 roles son is_system_role=true. No existe UI para crear roles custom (e.g., "Médico deportivo", "Community manager"). La columna is_system_role anticipa esto pero no hay implementación.
GAP-011	Sin módulo de gestión de planes de membresía	Operativo	Las tablas existen (gym.planes) pero no hay UI completa para crear/editar planes desde el dashboard del gerente.

FASE 10 — AUDITORÍA FINAL OBLIGATORIA
Análisis de dependencias
1. ¿Ningún usuario puede acceder a información de otro tenant?

✅ CONFIRMADO con matices:

Tablas public schema: RLS con tenant_id = fn_current_tenant_id() en codes, code_usages, user_roles, code_grants, audit_logs.
Tablas gym schema: RLS con id_gimnasio = gym.current_gym_id() en usuarios, gimnasios, accesos, etc.
RPCs sensibles: SECURITY DEFINER con SET search_path explícito.
Riesgo residual (GAP-013): gym.accesos.ver asignado a Miembro — no confirmado que la RLS filtre solo sus propios accesos vs todos los del gym.

2. ¿Los permisos respetan el aislamiento por tenant?

✅ CONFIRMADO:

fn_has_permission() llama fn_current_tenant_id() internamente → tenant siempre del JWT del usuario autenticado.
fn_create_staff_code() valida que el rol pertenezca al mismo tenant antes de crear.
Migración 017 añade c.tenant_id = v_gym_tenant en el consumo del staff_code.
3. ¿Los códigos de invitación no rompen el modelo de seguridad?

✅ CONFIRMADO tras migraciones 016+017:

Tipo restringido a USER_INVITE.
Tenant filtrado en lookup.
FOR UPDATE elimina race condition de consumo.
Frontend pre-valida con tenant_id correcto.
Trigger es la fuente de verdad; frontend es solo UX.
4. ¿Las recomendaciones no generan deuda técnica innecesaria?

Las recomendaciones de este documento no proponen nuevas abstracciones. Proponen completar funcionalidades que las tablas y RPCs ya anticipan (is_system_role, max_licenses, expires_at, audit_logs).

5. ¿Las recomendaciones son compatibles con la arquitectura actual?

Sí. Todo lo propuesto se implementa sobre:

Tablas existentes (public.roles, public.user_roles, public.codes, public.audit_logs)
RPCs existentes (fn_has_permission, fn_my_permissions, fn_revoke_code, fn_create_staff_code)
Clientes Supabase existentes (supabase + supabasePublic)
Contexto de autenticación existente (AuthProvider con permissions[])
