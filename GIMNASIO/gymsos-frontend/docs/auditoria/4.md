DA-01 — Dashboards de Cajero y Supervisor
Pregunta: ¿Los roles Cajero y Supervisor, que existen en el RBAC pero no tienen dashboard, comparten interfaz con otros roles o reciben dashboards propios?

Alternativas
Alternativa	Descripción
A	Dashboards completamente independientes para cada rol
B	Dashboard compartido con visibilidad condicional basada en permisos
C	Supervisor hereda el dashboard de Gerente restringido; Cajero hereda el de Recepcionista restringido
Análisis
Dimensión	Alt A — Propios	Alt B — Compartido	Alt C — Herencia
Coherencia UX	★★★★★ Cada rol tiene su identidad visual	★★★☆☆ Un solo dashboard con elementos que aparecen/desaparecen	★★★☆☆ Confusión de identidad
Esfuerzo inicial	★★☆☆☆ Mayor: dos rutas nuevas, dos sidebars	★★★★☆ Menor: un sistema de visibilidad	★★★☆☆ Medio: fork de dos dashboards existentes
Mantenibilidad	★★★★★ Cambios por rol no afectan otros	★★☆☆☆ Un cambio puede romper múltiples roles	★★★☆☆ Deuda de sincronización
Escalabilidad	★★★★★ Añadir nuevos roles es trivial	★★★☆☆ La lógica de visibilidad crece con cada rol	★★☆☆☆ La herencia se complica con el tiempo
Riesgo de seguridad	★★★★★ Bajo: cada ruta está explícitamente protegida	★★★☆☆ Medio: un bug en la visibilidad condicional puede exponer datos	★★★☆☆ Medio: herencia puede filtrar elementos no deseados
Riesgos específicos
Alt B: Si un widget del dashboard compartido usa una llamada a datos sin verificar el permiso correcto, un Cajero podría ver datos financieros del Gerente. El riesgo de regresión de seguridad es real.
Alt C: El dashboard de Supervisor basado en el Gerente empieza a crecer en complejidad hasta que es inmanejable mantenerlo como "gerente menos X cosas".
Veredicto final: Alternativa A — Dashboards propios
Justificación vinculante: Los roles Cajero y Supervisor son funcionalmente distintos entre sí y distintos de los roles existentes. El Cajero tiene un único objetivo (procesar pagos) que justifica una interfaz mínima y sin distracción. El Supervisor tiene un perfil de gestión que la recepcionista nunca tendrá. La inversión inicial de dos dashboards nuevos es recuperada inmediatamente en mantenibilidad y en ausencia de bugs de visibilidad. La infraestructura ya soporta esto: public.roles ya tiene ambos roles, ROUTE_ALLOWED_ROLES acepta nuevas entradas, el trigger handle_new_user acepta el string de rol desde metadata.

Implicaciones concretas:

Añadir "supervisor" y "cajero" al array ROLES en roles.ts
Crear rutas /dashboard/supervisor/ y /dashboard/cajero/ en el App Router
Añadir protección de rutas en el middleware para ambos roles
El string gym.usuarios.rol acepta los valores "supervisor" y "cajero" (compatible con el trigger existente)
DA-02 — Unificación de Roles Legacy vs RBAC
Pregunta: ¿Cómo se reconcilia el campo gym.usuarios.rol (string legacy, controla enrutamiento) con public.user_roles (RBAC moderno, controla autorización)? ¿Coexisten o se migra a un único sistema?

Alternativas
Alternativa	Descripción
A	Coexistencia controlada: string para routing, RBAC para autorización
B	Migración completa: eliminar el string, todo pasa por public.user_roles
C	Migración parcial: el middleware lee el rol desde JWT claims; el string se mantiene solo en la BD para compatibilidad
Análisis
Dimensión	Alt A	Alt B	Alt C
Riesgo de regresión	Bajo	Muy alto	Medio
Correctitud arquitectónica	Media	Alta	Alta
Costo de implementación	Bajo (1-2 días)	Alto (1-2 semanas + testing)	Medio (3-5 días)
Seguridad actual	Media (cookie XSS)	Alta	Alta
Deuda técnica generada	Media (documenta el dual)	Ninguna	Baja
Riesgos específicos
Alt B: El AuthProvider, el middleware, todos los hooks de permisos (usePermissions), el sidebar y la lógica de redirección post-login dependen del string gymsos_rol. Una migración implica modificar 15-20 archivos simultáneamente, con riesgo de regresión en la sesión de usuario. Sin una batería de tests E2E sólida, este riesgo es inaceptable en el estado actual del proyecto.
Alt A riesgo residual: La cookie gymsos_rol legible por JavaScript es el punto débil. Si un script XSS puede leer la cookie, puede saber qué rol tiene el usuario. Si puede modificarla, puede cambiar el dashboard que se carga (pero NO puede escalar privilegios reales porque la BD tiene RLS y fn_has_permission() como defensa real).
Veredicto final: Alternativa C — Coexistencia evolucionada (string en BD, JWT en middleware)
Justificación vinculante: La Alternativa A pura mantiene la cookie JavaScript, lo cual es un riesgo de seguridad documentado. La Alternativa B tiene demasiado riesgo de regresión. La Alternativa C es el punto óptimo: el middleware de Next.js lee el rol desde el JWT de Supabase (firmado, no manipulable desde JavaScript), no desde una cookie plain. El campo gym.usuarios.rol se mantiene en la BD para compatibilidad con las consultas existentes y como fuente de verdad del "dashboard de destino". El JWT claims se actualiza cada vez que el rol cambia en BD (vía trigger o función que llama a supabase.auth.admin.updateUser con app_metadata).

Política formal vinculante:


gym.usuarios.rol  → fuente de verdad del dashboard de destino
                  → se replica en JWT app_metadata.role al crear/actualizar usuario
                  → el middleware lee del JWT, no de cookie JavaScript
                  → el string NUNCA se usa para autorizar operaciones

public.user_roles → fuente de verdad para autorización de operaciones
                  → consultado via fn_has_permission() en Server Actions
                  → fn_has_permission() valida tenant + permisos + expires_at
                  → es la única defensa de seguridad real

Cookie gymsos_rol → deprecar su uso en el middleware (reemplazar por JWT)
                  → si se mantiene por compatibilidad: marcar como HttpOnly + Secure
                  → nunca usarla para decisiones de autorización

DA-03 — Futuro del Rol "Cliente"
Pregunta: El rol cliente existe en roles.ts y tiene su propio dashboard idéntico al de miembro. No existe en la migración 016 del RBAC. ¿Qué se hace con él?

Alternativas
Alternativa	Descripción
A	Deprecar como rol independiente. Redirigir a /dashboard/miembro. Eliminar el dashboard de cliente.
B	Definir como "cliente de otro módulo del SaaS" (no-gym) y darle un propósito real.
C	Convertir en "miembro premium" con experiencia diferenciada.
D	Mantener sin cambios por ahora. No tocar.
Análisis
Dimensión	Alt A	Alt B	Alt C	Alt D
Claridad arquitectónica	★★★★★	★★★★☆	★★★★☆	★☆☆☆☆
Esfuerzo	Bajo	Alto	Alto	Ninguno
Deuda técnica	Elimina deuda	Crea nueva	Crea nueva	Mantiene deuda
Riesgo de regresión	Bajo (con alias)	Medio	Medio	Ninguno
Riesgos específicos
Alt B/C: Inventar un propósito para un rol que no lo tiene crea más confusión. Si el negocio en el futuro necesita un "miembro premium", se diseña desde cero con criterio, no se rehabilita un rol existente sin historia.
Alt D: La deuda crece. Dos dashboards idénticos que mantener. Dos entradas en roles.ts. Posible confusión para nuevos desarrolladores que no saben cuál usar.
Veredicto final: Alternativa A — Deprecar y redirigir
Justificación vinculante: No existe evidencia documentada de que cliente tenga un propósito distinto a miembro. La hipótesis más probable (fue un vestigio de diseño) justifica eliminarlo como sistema de routing independiente. Se ejecuta como transición suave en 3 pasos: (1) en el AuthProvider, si rol = 'cliente' → redirigir a /dashboard/miembro; (2) mantener /dashboard/cliente como página que solo redirige; (3) en una migración futura, actualizar los registros gym.usuarios.rol = 'cliente' a 'miembro'. El RBAC ya asigna rol Miembro a todos los usuarios sin staff_code (handle_new_user línea 703-718), por lo que el RBAC ya está correcto.

DA-04 — Validación de max_licenses
Pregunta: ¿Dónde se valida que un gym no supere su límite de licencias de personal al generar un código de staff?

Alternativas
Alternativa	Descripción
A	Backend exclusivo: fn_create_staff_code() valida antes de crear el código
B	Frontend exclusivo: la UI verifica el conteo antes de mostrar el formulario
C	Ambos niveles: frontend como UX, backend como garantía de seguridad
Análisis
Dimensión	Alt A	Alt B	Alt C
Seguridad	★★★★★ La BD es la única fuente de verdad	★★☆☆☆ Bypasseable con llamada directa a RPC	★★★★★ Doble protección
Esfuerzo	Bajo	Bajo	Medio
Experiencia de usuario	★★★☆☆ Error solo al intentar crear	★★★★★ Feedback proactivo antes de intentar	★★★★★ Mejor UX posible
Riesgos específicos
Alt B: Cualquier cliente que llame directamente a fn_create_staff_code() (postman, script, frontend alternativo) puede ignorar la validación del frontend y crear códigos ilimitados. En un modelo SaaS con planes de precios, esto equivale a fraude.
Alt A puro: El usuario llena el formulario completo, hace clic en "Generar código" y recibe un error. La UX es subóptima.
Veredicto final: Alternativa C — Doble validación (Backend obligatorio + Frontend proactivo)
Justificación vinculante: La seguridad del límite de licencias protege la monetización del negocio. La validación en el backend es no negociable. La validación en el frontend es una cortesía de UX: si el admin ya alcanzó su límite, el formulario muestra el contador "10 de 10 licencias usadas" y el botón "Generar código" está deshabilitado con un tooltip explicativo y un link de upgrade.

Contrato de la RPC:

Input: p_tenant_id, p_role_id, opcionales de duración y usos
Validación 1: El rol pertenece al tenant (ya implementado)
Validación 2 (nueva): COUNT(*) FROM user_roles WHERE tenant_id = p_tenant_id AND (expires_at IS NULL OR expires_at > now()) < tenants.max_licenses
Si falla: { ok: false, error: 'LIMIT_REACHED', current: N, max: M }
Excepción: max_licenses IS NULL = plan Enterprise = ilimitado
DA-05 — Estrategia de Revocación de Staff
Pregunta: Cuando un trabajador deja el gym, ¿cómo se revocan sus permisos?

Alternativas
Alternativa	Descripción
A	Revocación física: DELETE FROM user_roles WHERE user_id = X
B	Revocación lógica: UPDATE user_roles SET expires_at = now()
C	Soft-delete con estado: campo status en user_roles (active, suspended, revoked)
D	Combinación: lógica + tabla de historial de revocaciones separada
Análisis
Dimensión	Alt A	Alt B	Alt C	Alt D
Historial de acceso	❌ Se pierde	✅ Se preserva	✅ Se preserva	✅ Se preserva
Complejidad de la BD	★★★★★ Mínima	★★★★★ Mínima	★★★★☆ Un campo extra	★★★☆☆ Dos tablas
Compatibilidad con fn_has_permission	★★★★★	★★★★★ Ya verifica expires_at	★★★☆☆ Requiere cambio en la función	★★★☆☆
Revertiblidad	❌ Irreversible	✅ Fácil (expires_at = NULL)	✅ Fácil (status = 'active')	✅
Capacidad de auditoría	★★☆☆☆ Solo lo que quedó en audit_logs	★★★★☆ La fila existe con el timestamp	★★★★★ Estado explícito en la fila	★★★★★
Riesgos específicos
Alt A: En un incidente de seguridad post-baja del trabajador, no se puede demostrar cuándo exactamente perdió el acceso. La fila fue eliminada. El audit_log tiene la acción, pero la fila original no existe para contrastar.
Alt C: fn_has_permission() actualmente no verifica un campo status, solo expires_at. Requiere modificación de la función más usada en el sistema.
Alt D: Añade complejidad sin beneficio adicional sobre Alt B + campos extra en la fila.
Veredicto final: Alternativa B + campos de contexto en la fila
Justificación vinculante: fn_has_permission() ya verifica expires_at IS NULL OR expires_at > now(). No se requiere ningún cambio en la función de autorización. SET expires_at = now() es un cambio atómico que invalida instantáneamente todos los permisos del trabajador. La fila se preserva para auditoría con el timestamp exacto de la revocación.

Campos adicionales recomendados en user_roles (en migración 018):

revoked_by UUID REFERENCES auth.users(id) — quién ejecutó la revocación
revocation_reason TEXT — motivo (renuncia / despido / suspensión / vencimiento de contrato)
revocation_type TEXT CHECK IN ('permanent', 'temporary') — si es definitiva o temporal
Flujo completo de revocación:


Admin → click "Revocar Acceso"
  → Modal: campo "Motivo" (obligatorio) + tipo (Temporal/Definitivo)
  → Si Temporal: selector de fecha de reactivación
  → Si Definitivo: checkbox de confirmación
  → Acción: UPDATE user_roles SET
      expires_at = now(),
      revoked_by = auth.uid(),
      revocation_reason = $motivo,
      revocation_type = $tipo
    WHERE user_id = $target AND tenant_id = $tenant
  → INSERT audit_logs (actor, action='ROLE_REVOKED', target, metadata)
  → La próxima llamada del trabajador a fn_has_permission() retorna FALSE
  → El middleware redirige al login con mensaje "Tu acceso ha sido revocado"
DA-06 — Permisos Específicos de Staff
Pregunta: ¿El módulo de gestión de staff necesita permisos RBAC propios o se puede usar gym.codigos.crear como proxy?

Alternativas
Alternativa	Descripción
A	Usar gym.codigos.crear como proxy para "puede gestionar staff"
B	Crear gym.staff.ver y gym.staff.gestionar como permisos independientes
C	Crear un conjunto completo: gym.staff.ver, gym.staff.gestionar, gym.staff.revocar
Análisis
El problema de la Alternativa A es semántico pero tiene consecuencias reales: "puede crear códigos" y "puede ver la lista de trabajadores y sus permisos" son responsabilidades distintas. Un Supervisor podría necesitar ver quiénes son sus colegas (staff.ver) sin poder crear nuevos códigos de ingreso. Si se usa gym.codigos.crear como proxy, se tendría que dar al Supervisor el permiso de crear códigos, lo cual es incorrecto desde una perspectiva de seguridad (los códigos de staff son sensibles).

La Alternativa C añade gym.staff.revocar pero en la práctica la revocación es una capacidad de gestión y puede estar incluida en gym.staff.gestionar sin crear un permiso separado por ahora.

Veredicto final: Alternativa B — Dos permisos nuevos: gym.staff.ver y gym.staff.gestionar
Justificación vinculante: La separación semántica tiene valor operativo inmediato. El Supervisor puede ver el listado de su equipo (staff.ver) sin poder modificar roles ni crear códigos (staff.gestionar). El Administrador General tiene ambos. Ningún otro rol necesita acceso al módulo de staff. La implementación en migración 018 es trivial: dos inserts en cat_permissions y la asignación correcta en role_permissions.

DA-07 — Estrategia de Auditoría de Acciones
Pregunta: ¿El visor de auditoría usa la tabla existente public.audit_logs (migración 015b) o requiere infraestructura adicional?

Alternativas
Alternativa	Descripción
A	Usar public.audit_logs existente, añadir los triggers faltantes en migración 018
B	Crear una tabla gym.activity_log específica del módulo gym con estructura simplificada
C	Usar un servicio externo (Datadog, Mixpanel) para el audit trail
Análisis
La Alternativa B duplica funcionalidad. La Alternativa C introduce dependencia externa y costo de integración sin beneficio claro en esta etapa. La Alternativa A es la correcta: la tabla ya existe, ya tiene estructura adecuada (actor_id, action, target_table, target_id, old_data JSONB, new_data JSONB, created_at), y ya está siendo escrita por algunos triggers. Lo que falta es cobertura completa.

Veredicto final: Alternativa A — Tabla existente con cobertura ampliada
Eventos que DEBEN registrarse en audit_logs (verificar en migración 018):

Evento	Acción en audit_logs	Disparado por
Registro de nuevo miembro	MEMBER_CREATED	Trigger en gym.usuarios
Cambio de rol de staff	ROLE_CHANGED	Trigger en public.user_roles UPDATE
Revocación de acceso	ROLE_REVOKED	Trigger en public.user_roles UPDATE (cuando expires_at se establece)
Creación de código de staff	CODE_CREATED	Trigger en public.codes INSERT WHERE type='USER_INVITE'

Procesamiento de pago	PAYMENT_CREATED	Trigger en gym.pagos INSERT

Cambio de configuración del gym	GYM_CONFIG_UPDATED	Trigger en gym.gimnasios UPDATE
Acceso denegado	ACCESS_DENIED	Ya en gym.accesos WHERE permitido=false — añadir log
Formato de cada fila en audit_logs:


actor_id:     UUID del usuario que ejecutó la acción
actor_role:   Nombre del rol del actor al momento de la acción
action:       String canónico (MEMBER_CREATED, ROLE_REVOKED, etc.)
target_table: Tabla afectada ('gym.usuarios', 'public.user_roles', etc.)
target_id:    UUID del registro afectado
old_data:     JSONB con valores anteriores (para UPDATEs)
new_data:     JSONB con valores nuevos
tenant_id:    UUID del gimnasio (para tenant isolation en la UI)
ip_address:   Disponible vía Supabase Auth metadata (Fase C)
created_at:   Timestamp preciso

│      ├── Busca code_grants del staff_code                           │
│      ├── INSERT public.user_roles (rol del code_grants)             │
│      ├── UPDATE public.codes (current_uses + 1, status si lleno)   │
│      └── INSERT public.code_usages (registro del uso)              │
│                                                                     │
│  11. Trabajador es redirigido a su dashboard según su rol           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

ESTADO FINAL EN BD:
  public.user_roles:  user_id=X, tenant_id=Y, role_id=Z (Recepcionista)
  gym.usuarios.rol:   'recepcionista'
  public.codes:       status='used' (si max_uses=1)
  public.code_usages: registro permanente del evento

ACTOR: Administrador General
DISPARADOR: Renuncia, despido, vacaciones, fin de contrato

┌─────────────────────────────────────────────────────────────────────┐
│                    FLUJO: REVOCACIÓN DE ACCESO                      │
│                                                                     │
│  [ADMINISTRADOR GENERAL]                                            │
│                                                                     │
│  1. Navega a /dashboard/admin/staff → Tab "Trabajadores Activos"    │
│  2. Encuentra al trabajador. Click "Revocar Acceso"                 │
│  3. Modal de confirmación:                                          │
│     ├── Campo: Motivo (obligatorio)                                 │
│     ├── Tipo: Temporal (con fecha reactivación) / Definitivo        │
│     └── Para definitivo: checkbox de confirmación                   │
│  4. Sistema ejecuta:                                                │
│     UPDATE public.user_roles SET                                    │
│       expires_at = now(),                                           │

│       revocation_reason = $motivo,                                  │
│       revocation_type = $tipo                                       │
│     WHERE user_id = $target AND tenant_id = $tenant                 │

│                                                                     │

  expires_at IS NULL       → Activo indefinido

  expires_at <= now()      → Expirado/Revocado (sin acceso)

2.7 Cómo se Asignan y Modifican Roles

FLUJO DE ASIGNACIÓN DE ROL (post-onboarding):

CASO NORMAL: Mediante código de staff (el más común)
  → Admin genera código para rol específico
  → Trabajador se registra con el código
  → Trigger asigna el rol automáticamente (handle_new_user CASO B)

CASO ESPECIAL: Cambio de rol de trabajador existente
  → Admin va a /dashboard/admin/staff
  → Selecciona trabajador → "Editar rol"
  → Selecciona nuevo rol del dropdown
  → Sistema:
      UPDATE public.user_roles SET role_id = $nuevo_rol
      UPDATE gym.usuarios SET rol = $string_nuevo_rol
      UPDATE auth.users app_metadata.role (via Supabase Admin API)
      INSERT audit_logs (ROLE_CHANGED, old_role, new_role, actor)

CASO TEMPORAL: Expiración de rol (contratos temporales)
  → Al crear el código de staff: configurar expires_at
  → Al asignar el rol: especificar expires_at en user_roles
  → Cuando expires_at llega: fn_has_permission retorna FALSE
  → Widget en dashboard admin: "3 roles expiran esta semana"

4.2 Reglas de Acceso y Protección de Rutas
Verificación en el middleware (en orden de ejecución):


Paso 1: Sesión válida
  ¿Existe session válida de Supabase?
  NO → /login
  SÍ → Paso 2

Paso 2: Rol y destino
  ¿El JWT app_metadata.role tiene una ruta en role_dashboard_map?
  NO → /login (error: rol no reconocido)
  SÍ → Paso 3

Paso 3: Autorización de ruta
  ¿La ruta solicitada está en ROUTE_ALLOWED_ROLES para el rol del JWT?
  NO → redirigir al dashboard propio del rol
  SÍ → Paso 4

Paso 4 (solo rutas críticas): Verificación de permiso específico
  Rutas críticas: /admin/staff, /admin/auditoria, /admin/configuracion,
                  /admin/reportes, /staff/*, /cajero/*
  ¿fn_has_permission(permiso_requerido_de_la_ruta) = TRUE?
  NO → Error 403
  SÍ → Acceso concedido

7.7 Riesgos Futuros Identificados
Riesgo 1 — Crecimiento del cat_permissions sin governance

Si cada módulo nuevo añade permisos sin un proceso de revisión, la matriz de permisos se vuelve inmanejable. Mitigación: Establecer una convención: {módulo}.{recurso}.{acción}. Cualquier permiso nuevo requiere documentación en cat_permissions con description explícita. Nunca crear permisos "comodín".

Riesgo 2 — Sincronización JWT/BD en cambios de rol

Si el rol cambia en gym.usuarios.rol pero no se actualiza app_metadata.role en el JWT de Supabase Auth, el usuario seguirá viendo el dashboard de su rol anterior hasta que su sesión expire. Mitigación: Cualquier cambio de rol debe incluir obligatoriamente la llamada a supabase.auth.admin.updateUser como parte del mismo flujo (o trigger que lo dispare).

Riesgo 3 — Expiración masiva de roles

Si un gym tiene 20 contratos temporales que expiran el mismo día, 20 trabajadores perderán acceso simultáneamente. Si no hay UI de renovación masiva, el admin tendrá que reactivarlos de uno en uno. Mitigación (Fase C): Widget de "roles que expiran esta semana" con opción de renovación en bulk.

Riesgo 4 — Crecimiento de audit_logs

Con 100+ gyms y triggers en cada operación, audit_logs crecerá rápidamente. Sin particionamiento o política de retención, las queries se volverán lentas. Mitigación (Fase E): Implementar particionamiento por created_at (mensual) y política de archivado después de 2 años.

Riesgo 5 — fn_has_permission como bottleneck

Si cada Server Action llama a fn_has_permission() y esta función hace una query a user_roles JOIN role_permissions, a escala puede ser un punto de contención. El AuthProvider ya cachea los permisos en sesión — este riesgo está mitigado para operaciones de UI. Para Server Actions críticas, el caché de sesión no siempre aplica. Mitigación: Evaluar en Fase E si el caché de permisos necesita un TTL explícito o un mecanismo de invalidación.
