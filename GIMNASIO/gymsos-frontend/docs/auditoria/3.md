PARTE 1 — RESOLUCIÓN DE GAPS
Clasificación consolidada (GAPs de ambas auditorías, sin duplicados)
Grupo A — Críticos de Seguridad y Operación
GAP-C01 | Doble sistema de roles no sincronizado

Problema: gym.usuarios.rol (string legacy) controla el enrutamiento de dashboards. public.user_roles (RBAC moderno) controla la autorización funcional. Son independientes. Un Cajero tiene permisos en user_roles pero no tiene ruta de dashboard porque no existe como string en roles.ts. Si alguien manipula la cookie gymsos_rol, puede intentar acceder a rutas para las que no tiene permisos RBAC reales.
Resolución: Ver DA-02. Se define una política de coexistencia controlada: el string antiguo sigue siendo la fuente de enrutamiento inicial, pero el middleware de rutas se refuerza con verificación de permiso real mediante fn_has_permission(). El string se mantiene como "alias de dashboard", no como autorización.
Acción requerida: Reforzar middleware. Añadir tabla role_dashboard_map que mapea cada nombre de rol RBAC a su ruta de dashboard. Ver PARTE 2, DA-02.
GAP-C02 | Cajero y Supervisor sin ruta de dashboard

Problema: Los roles Cajero (hierarchy 30) y Supervisor (hierarchy 10) existen en public.roles con 9 y 20 permisos respectivamente. Sin embargo, no existen en roles.ts ni tienen ruta /dashboard/cajero ni /dashboard/supervisor. Un usuario con cualquiera de estos roles queda huérfano al iniciar sesión.
Resolución: Ver DA-01. Se crean dashboards propios. Ver PARTE 4 y PARTE 5 para el diseño completo.
Acción requerida: Dos nuevas rutas de dashboard. Dos entradas en roles.ts. Una entrada en role_dashboard_map.
GAP-C03 | Sin UI para revocar roles de staff

Problema: fn_revoke_code() existe en BD pero no tiene pantalla. Un trabajador que deja el gym mantiene sus permisos RBAC indefinidamente mientras su user_roles esté activo. La única opción actual es intervención directa en la base de datos.
Resolución: El panel de Staff Management del Administrador General incluye acción "Revocar Acceso" que ejecuta SET expires_at = now() en user_roles. Ver DA-05 y PARTE 3, Módulo de Staff.
Acción requerida: Pantalla /dashboard/admin/staff con acción de revocación. RPC de soporte.
GAP-C04 | Registro de miembro no es atómico

Problema: El flujo de registro crea primero en auth.users (externo, no transaccionable) y luego inserta en gym.usuarios, membresias, pagos en pasos separados. Si cualquier paso falla, queda un usuario huérfano en Supabase Auth sin perfil ni membresía.
Resolución: El trigger handle_new_user ya mitiga esto en la creación de perfil. Para la membresía y pago, se requiere una RPC transaccional rpc_registrar_nuevo_miembro que ejecute en una sola transacción PL/pgSQL: INSERT usuarios (si no existe) + INSERT membresias + INSERT pagos. Si falla, la llamada a supabase.auth.admin.deleteUser(authUserId) limpia el usuario Auth.
Acción requerida: RPC transaccional en migración. Frontend llama RPC después del signUp exitoso.
GAP-C05 | Cookie gymsos_rol legible por JavaScript

Problema: La cookie que identifica el rol del usuario en el frontend puede ser leída y potencialmente modificada por scripts. Si bien la BD tiene RLS y fn_has_permission() como defensa real, el enrutamiento y la visibilidad de UI pueden ser manipulados.
Resolución: Ver DA-02. La cookie se convierte en HttpOnly en el servidor. El rol se lee desde los JWT claims (app_metadata.role) en el middleware de Next.js. No se accede desde el cliente JavaScript.
Acción requerida: Cambio en la capa de autenticación del servidor. No requiere migración.

Problema: gym.planes existe con datos pero la UI no permite crear, editar ni activar/desactivar planes.
Resolución: Se mueve a la pestaña "Planes" dentro de Configuración. Ver AD-08.

PARTE 2 — DECISIONES ARQUITECTÓNICAS DA-01 A DA-07
DA-01 | ¿Cajero y Supervisor tienen dashboards propios o comparten con otro rol?
Opciones analizadas:

(a) Dashboards propios — rutas /dashboard/supervisor y /dashboard/cajero
(b) Comparten con recepcionista/gerente pero con módulos ocultos según permisos
Análisis:

La opción (b) parece más eficiente pero introduce un anti-patrón de diseño: si el dashboard de recepcionista tiene 4 módulos y el de supervisor tiene 15, no tienen la misma naturaleza — el "dashboard de recepcionista con módulos extras" sería en realidad el dashboard del supervisor mal nombrado.

La opción (a) tiene un costo real: dos rutas nuevas, dos sidebars, dos páginas de inicio. Pero garantiza que cada rol tiene una experiencia coherente y sin elementos grises que "aparecen o desaparecen según quién mira". Esto también es más fácil de mantener a largo plazo: si el Supervisor necesita un widget nuevo, se añade en su dashboard sin tocar el del Gerente.

Veredicto: Opción A — Dashboards propios.

Justificación de negocio: El Supervisor es un rol de alto valor operativo. Su dashboard debe inspirar confianza de gestión, no parecer un dashboard de recepcionista con extras. El Cajero tiene una tarea muy específica (cobrar) y se beneficia de una pantalla orientada exclusivamente a transacciones, sin distracción.

Justificación técnica: El sistema ya tiene la infraestructura (roles en public.roles, permisos en cat_permissions, middleware con ROUTE_ALLOWED_ROLES). Añadir dos rutas es una extensión, no un rediseño.

Implementación:

Nueva entrada en roles.ts: "supervisor" y "cajero" en el array ROLES
Nuevas rutas: /dashboard/supervisor/ y /dashboard/cajero/
Entradas en ROUTE_ALLOWED_ROLES: supervisor → ["supervisor", "admin"], cajero → ["cajero", "admin"]
El string en gym.usuarios.rol se puede asignar como "supervisor" y "cajero" — compatibles con el trigger handle_new_user que ya acepta el rol desde raw_user_meta_data->>'rol'
DA-02 | ¿Cómo se sincroniza gym.usuarios.rol con public.user_roles?
Opciones analizadas:

(a) Mantener dual: string para routing, RBAC para autorización
(b) Migrar a un único sistema: eliminar el string, todo pasa por RBAC
Análisis:

La opción (b) es la arquitecturalmente correcta pero tiene un costo de migración significativo: el middleware de rutas, el sidebar, todos los hooks que usan useUser() o usePermissions(), y el AuthProvider dependen actualmente del string gymsos_rol. Una migración completa significaría tocar 15-20 archivos y requeriría un período de transición con riesgo de regresiones.

La opción (a) permite avanzar sin romper nada existente, pero introduce una regla de diseño que hay que documentar y hacer cumplir: el string es un alias para la experiencia de usuario, nunca para la seguridad.

Veredicto: Opción A con blindaje de seguridad — Coexistencia controlada y documentada.

Justificación técnica: El riesgo de seguridad real de la doble capa está en el middleware de rutas. Si el middleware solo verifica el string (cookie) sin verificar un permiso real, alguien que modifique la cookie podría ver una ruta. La solución es reforzar el middleware: para rutas críticas (financiero, configuración, staff), el middleware verifica ADEMÁS un permiso RBAC real con una llamada al servidor. Para rutas de baja sensibilidad (visualización), el string es suficiente.

La cookie gymsos_rol se convierte en HttpOnly en el servidor (no JavaScript) y se firma (no solo un string plain). Esto elimina el riesgo XSS.

Política formal que queda documentada:


gym.usuarios.rol  → determina qué dashboard se carga al iniciar sesión
                  → determina el label visible del rol en la UI
                  → NO autoriza operaciones

public.user_roles → determina qué puede hacer el usuario en cada operación
                  → consultado via fn_has_permission() en el servidor
                  → es la fuente de verdad para seguridad
Regla de mapeo (nueva tabla conceptual role_dashboard_map):

Nombre en gym.usuarios.rol	Dashboard route	Nombre en public.roles
gerente / admin	/dashboard/admin	Administrador General
supervisor	/dashboard/supervisor	Supervisor
cajero	/dashboard/cajero	Cajero
recepcionista	/dashboard/recepcionista	Recepcionista
entrenador	/dashboard/entrenador	Entrenador
nutricionista	/dashboard/nutricionista	Nutricionista
miembro	/dashboard/miembro	Miembro
Esta tabla no necesita ser una tabla SQL — puede ser un objeto de configuración en el código. Lo importante es que es la única fuente de verdad para el mapeo.

DA-03 | ¿El rol "cliente" se elimina, unifica con "miembro" o se define con propósito específico?
Análisis:

La auditoría v2 identificó que "cliente" no está en la migración 016 (no tiene public.roles con ese nombre), pero sí existe en roles.ts y tiene su propio dashboard que es funcionalmente idéntico al de "miembro". La hipótesis es que fue un vestigio de un momento en que el sistema consideraba distinguir entre un "miembro de gym" (paga membresía) y un "cliente" (cliente de otro módulo del SaaS, no del gym).

Veredicto: Deprecar como rol independiente. Unificar en "miembro" con campo nivel.

Justificación de negocio: No existe diferenciación real de experiencia hoy. Mantenerlo crea deuda de documentación, confusión para nuevos desarrolladores, y código duplicado. Si en el futuro se necesita una experiencia "premium" para miembros, se implementa como un campo nivel: 'básico' | 'premium' en gym.usuarios o gym.membresias, no como un rol separado.

Plan de transición:

En el AuthProvider, si el usuario tiene rol = 'cliente', se le enruta al dashboard de miembro (/dashboard/miembro)
El dashboard de /dashboard/cliente se mantiene como alias que redirige a /dashboard/miembro
En el RBAC, los usuarios que tenían rol = 'cliente' se les asigna el rol RBAC Miembro
En una fase posterior, el string cliente en gym.usuarios.rol se migra a miembro
DA-04 | ¿max_licenses se valida en el backend o en el frontend?
Veredicto: Backend (BD) — obligatorio, no negociable.

Justificación de seguridad: Cualquier validación que solo existe en el frontend puede ser omitida por cualquier cliente que llame directamente a la RPC. La validación de límites de licencias afecta directamente la monetización del negocio. Un gym que paga por 5 licencias no puede tener 20 trabajadores por una omisión en el frontend.

Implementación en fn_create_staff_code():
El procedimiento consulta public.tenants.max_licenses y compara con el conteo actual de user_roles activos en ese tenant. Si current_active_staff >= max_licenses, retorna { ok: false, error: 'LIMIT_REACHED', current: N, max: M }. El frontend muestra este error con un call-to-action para actualizar el plan.

Excepción: max_licenses = NULL significa ilimitado (plan Enterprise).

DA-05 | ¿La revocación de staff es física (DELETE) o lógica (expires_at)?
Veredicto: Lógica con expires_at = now() — preservación del historial obligatoria.

Justificación de negocio: Si se elimina la fila de user_roles, el sistema pierde la trazabilidad de "quién tuvo acceso cuándo". En un contexto de auditoría de seguridad, esto es inaceptable. Si hay un incidente de seguridad (acceso no autorizado, modificación de datos) y el trabajador ya fue dado de baja, la BD no puede probar que ese usuario ya no tenía acceso en ese momento porque la fila fue eliminada.

Justificación técnica: fn_has_permission() ya verifica expires_at IS NULL OR expires_at > now(). Establecer expires_at = now() automáticamente invalida todos los permisos sin ningún cambio en el código de verificación.

Flujo de revocación:

Admin hace clic en "Revocar Acceso" en la pantalla de staff
Sistema hace UPDATE user_roles SET expires_at = now() WHERE user_id = X AND tenant_id = Y
Se registra la acción en audit_logs con actor, objetivo, timestamp y motivo
El trabajador ve su próxima acción rechazada por fn_has_permission() → sistema lo redirige al login con mensaje "Tu acceso ha sido revocado"
Campo adicional recomendado: revoked_by UUID y revocation_reason TEXT en user_roles. Esto hace que la auditoría sea más rica que solo un timestamp.

DA-06 | ¿Se necesitan nuevos permisos RBAC para el módulo de administración de staff?
Veredicto: Sí — crear gym.staff.ver y gym.staff.gestionar.

Justificación: El módulo de Staff Management es funcionalmente distinto al de Códigos. Usar gym.codigos.crear como proxy para "puede ver la lista de trabajadores" mezcla dos responsabilidades. En el futuro, podría existir un Supervisor que vea la lista de staff (para supervisar) pero que no pueda crear códigos ni revocar accesos. Eso requiere permisos separados.

Asignación de nuevos permisos a roles:

gym.staff.gestionar	✅	❌	❌	❌
gym.evaluaciones.ver	✅	✅	❌	Entrenador ✅, Nutricionista ✅
gym.evaluaciones.gestionar	✅	❌	❌	Entrenador ✅, Nutricionista ✅
gym.asistencia.ver	✅	✅	❌	Entrenador ✅
Estos permisos se añaden en migración 018 a cat_permissions y se asignan a los roles mediante role_permissions.

DA-07 | ¿El visor de audit_logs usa la tabla existente o requiere tabla adicional?
Veredicto: Usar la tabla existente public.audit_logs de la migración 015b.

Justificación: La tabla ya existe, ya tiene triggers de escritura en acciones clave, y ya tiene los campos necesarios (actor_id, action, target_table, target_id, old_data, new_data, created_at). Crear una tabla paralela solo duplicaría datos.

Lo que sí se necesita es verificar que los eventos más importantes estén siendo registrados en audit_logs. Si hay acciones que no están siendo registradas (ej. cambios de permisos de rol, revocación de staff), se añaden los triggers correspondientes en migración 018.

PARTE 3 — DISEÑO COMPLETO DEL ADMINISTRADOR GENERAL
Principio de diseño rector
El Administrador General no opera el gym — lo gobierna. Su dashboard es un cockpit de decisiones, no un formulario de trabajo. Cada elemento en pantalla responde a una pregunta de negocio, no a una tabla de la base de datos.

3.1 Ruta: /dashboard/admin
Nombre de página: Panel Ejecutivo

Permiso requerido: Cualquier permiso del módulo gym (si tiene acceso al tenant, puede entrar). Protección adicional: gym.reportes.ver para las métricas financieras.

ZONA 1 — Pulso del Negocio (siempre visible, sin scroll)

Cinco KPI cards horizontales. Cada una tiene: número principal, etiqueta, variación respecto al período anterior (con flecha y color), y un color de fondo semáforo cuando hay alerta.

Card	Dato principal	Variación	Semáforo
Ingresos Hoy	S/ 2,450	+12% vs ayer	Verde > meta, Rojo < 80% meta
Accesos Hoy	87 / 200	43.5% del aforo	Amarillo si > 80%, verde si normal
Membresías Activas	234	-3 esta semana	Rojo si hay caída sostenida
En Riesgo (Churn)	23 miembros	+5 vs semana pasada	Rojo siempre si > 0
Staff Activo Hoy	6 / 8	2 sin check-in	Amarillo si alguien falta
ZONA 2 — Gráficos de Tendencia (60/40)

Izquierda (60%): Gráfico de líneas "Ingresos — últimos 12 meses". Dos series: año actual vs año anterior. Línea de meta mensual como referencia punteada. Al hover: tooltip con desglose por tipo de plan.

Derecha (40%): Gráfico de barras apiladas "Accesos por hora — hoy vs promedio de la semana". Muestra la hora pico y la hora valle. Útil para decisiones de horario de staff.

ZONA 3 — Alertas y Acciones Urgentes (50/50)

Izquierda: Membresías por Vencer (próximos 7 días)
Tabla compacta: Avatar + Nombre, Plan, Días restantes, Botón "Notificar".
Máximo 5 filas visibles. Link "Ver todas (N)" al módulo de miembros.
Ordenada por días restantes ascendente (más urgentes primero).

Derecha: Miembros en Riesgo de Abandono
Tabla compacta: Avatar + Nombre, Score de Churn (badge rojo/naranja), Último acceso (hace N días), Botón "Intervenir".
Máximo 5 filas visibles. Score viene de churn_predictions.
Ordenada por score descendente (mayor riesgo primero).

ZONA 4 — Snapshot Operativo (33/33/33)

Col 1: Clases de Hoy — Lista de clases con hora, nombre, entrenador, y barra de ocupación (X de Y inscritos). Badge "Llena" en rojo si sin cupo.

Col 2: Últimas Transacciones — 5 pagos más recientes con nombre, monto, forma de pago, hora. Badge de tipo de pago (Efectivo / Yape / Tarjeta).

Col 3: Staff del Día — Lista de trabajadores con avatar, nombre, rol, y estado (✅ Activo / ⚠️ No registrado). Badge de turno si aplica.

Acciones Rápidas (botones fijos en el header o barra flotante)

[+ Nuevo Miembro] — abre modal de registro rápido
[+ Código de Staff] — abre modal de generación de código
[🔍 Buscar Miembro] — abre búsqueda global Cmd+K
[📤 Exportar Reporte] — descarga reporte del día en PDF

4.1 Supervisor — /dashboard/supervisor
Perfil: Encargado de turno o jefe de operaciones. Tiene más autoridad que la recepcionista pero no toca la configuración ni las finanzas estratégicas.

Objetivo de la sesión: Supervisar que el gym esté operando correctamente, resolver incidencias que el personal de base no puede, y aprobar operaciones que requieren mayor jerarquía.

Pantalla de inicio:

Header KPIs (4 cards):

Accesos del turno actual
Membresías procesadas hoy
Clases en curso ahora
Incidencias pendientes (membresías sin pagar que intentaron entrar, accesos denegados)
Zona de acciones del turno:

Lista de membresías que vencen hoy — con botón "Aprobar renovación con descuento"
Lista de accesos denegados del día — con botón "Ver detalle" y "Autorizar excepción"
Clases con capacidad crítica (>90% ocupadas) — con botón "Abrir cupo extra"
Zona de supervisión de personal:

Staff activo en este momento con última acción registrada
Alertas de inactividad (recepcionista sin registrar acceso en 20 min durante horario pico)
Permisos requeridos: gym.staff.ver, gym.membresias.aprobar, gym.reportes.ver, gym.accesos.ver, gym.clases.gestionar

Lo que NO ve el Supervisor:

Reporte financiero estratégico (solo operativo)
Configuración del gym
Panel de creación de códigos de staff
Módulo de revocación de accesos
Audit logs completos
Sidebar del Supervisor:


🏠  Mi Turno (inicio)
👥  Miembros
   ├── Buscar miembro
   ├── Membresías por vencer
   └── Accesos denegados hoy
📅  Clases y Agenda
   └── Agenda del día
👨‍💼  Mi Equipo
   └── Staff activo ahora
📊  Reportes Operativos
   ├── Resumen del turno
   └── Accesos del día
4.2 Cajero — /dashboard/cajero
Perfil: Operador exclusivo de caja. Su pantalla es minimalista y orientada a transacciones. No gestiona accesos ni clases. Solo cobra.

Objetivo de la sesión: Procesar cobros de la manera más rápida posible. Cero fricción entre "miembro pide renovar" y "pago registrado".

Pantalla de inicio:

Header KPIs (3 cards):

Total cobrado en este turno (S/)
Número de transacciones del turno
Membresías por cobrar hoy (sin pagar, vencidas)
Zona central — Acción rápida de cobro:
Barra de búsqueda grande prominente: "Buscar miembro por nombre o documento"
Al seleccionar: muestra estado de membresía y botón de cobro inmediato.

Tabla "Cobros Pendientes del Día":
Membresías vencidas o por vencer hoy. Columnas: Nombre, Plan, Monto, Días vencido, Acción "Cobrar".

Historial del turno:
Últimas 10 transacciones con nombre, monto, forma de pago, hora.

Permisos requeridos: gym.pagos.crear, gym.pagos.ver, gym.membresias.crear, gym.membresias.ver, gym.usuarios.ver, gym.planes.ver

Lo que NO ve el Cajero:

Predicciones de churn
Gestión de clases
Staff y códigos
Auditoría
Configuración
Reportes financieros estratégicos (solo su caja del día)
Sidebar del Cajero:


💰  Mi Caja (inicio)
👤  Buscar Miembro
💳  Cobros
   ├── Pendientes hoy
   └── Historial del turno
📋  Membresías
   └── Ver estado por miembro
4.3 Recepcionista — /dashboard/recepcionista
Perfil: Front desk. Primera interacción con el miembro al llegar. Gestiona el flujo físico del gym: quién entra, quién se inscribe, quién tiene deuda pendiente.

Objetivo de la sesión: Control de acceso en tiempo real. La pantalla de inicio debe ser LIVE — actualización automática de quién entra y quién no puede entrar.

Pantalla de inicio:

Header KPIs (4 cards):

Accesos de hoy (entradas confirmadas)
Aforo actual (en el gym en este momento)
Membresías vencidas que intentaron entrar hoy
Clases próximas (en las siguientes 2 horas)
Zona central — Control de Acceso (LIVE):
Panel con sección "Últimos Accesos" con actualización en tiempo real (Supabase Realtime). Cada registro: Avatar, Nombre, Estado (✅ ENTRADA PERMITIDA / ❌ ACCESO DENEGADO), Hora, Tipo de membresía.

Input de escaneo QR visible y activo. Si se detecta código QR: muestra nombre del miembro, foto, estado de membresía, y da ENTER/DENEGADO automáticamente.

Sidebar derecho (alertas del día):

"María González — membresía vence hoy" → botón "Cobrar ahora"
"Carlos Pérez — 3er intento de acceso denegado" → botón "Ver perfil"
"Clase de Yoga inicia en 15 min — 2 cupos disponibles" → informativo
Permisos requeridos: gym.accesos.ver, gym.accesos.crear, gym.usuarios.ver, gym.usuarios.crear, gym.clases.ver, gym.clases.inscribir, gym.membresias.ver, gym.planes.ver

Lo que NO ve la Recepcionista:

Reportes financieros
Gestión de staff y códigos
Auditoría
Configuración
Churn predictions
Pagos (solo ve estado de membresía, no montos)
Sidebar de la Recepcionista:


⚡  Control de Acceso (inicio)      ← LIVE
👥  Miembros
   ├── Buscar miembro
   ├── Registrar nuevo miembro
   └── Vencimientos hoy
📅  Clases del Día
   ├── Horario de hoy
   └── Inscribir a clase
🆘  Soporte al Miembro

Objetivo: Dar al dueño el estado del negocio en 30 segundos.

Permisos requeridos: gym.reportes.ver + cualquier permiso del tenant

Fuentes de datos:

dashboard.service.getKPIsGerente() — ingresos, miembros, accesos
dashboard.service.getChurnAtRisk() — lista de riesgo
gym.clases JOIN gym.inscripciones — ocupación de clases
gym.usuarios WHERE rol IN ('recepcionista','entrenador','cajero','supervisor') — staff del día
Widgets:

5 KPI cards (Zona 1) — descritas en Parte 3
Gráfico ingresos 12 meses (líneas, comparativa año anterior)
Gráfico accesos por hora del día actual (barras)
Tabla "Membresías por vencer" (5 filas, link a más)
Tabla "Churn Risk" (5 filas, link a más)
Lista "Clases de hoy" con ocupación
Lista "Últimas transacciones" (5)
Lista "Staff del día" con estado
Acciones disponibles:

Notificar a miembro con membresía por vencer
Intervenir en miembro con alto riesgo de churn
Ver perfil de cualquier miembro
Botones de acceso rápido del header
Actualizaciones en tiempo real:

Zona de accesos: supabase.channel() en tabla gym.accesos
Widget de staff: polling cada 5 minutos
Página AD-02 — Lista de Miembros (/dashboard/admin/miembros)
Objetivo: Gestionar la cartera de miembros del gym.

Permisos requeridos: gym.usuarios.ver

Filtros disponibles:

Por estado de membresía: Activa / Por vencer / Vencida / Sin membresía
Por riesgo de churn: Alto / Medio / Bajo / Sin datos
Por plan: selección múltiple de planes disponibles
Por fecha de alta: rango de fechas
Búsqueda libre: nombre, email, documento
Columnas de la tabla:

Columna	Dato	Notas
Miembro	Avatar + Nombre + Email	Clickable → perfil
Membresía	Badge de estado (coloreado)	Activa / Por vencer / Vencida
Plan	Nombre del plan	
Vence en	Fecha + días restantes	Rojo si < 7 días
Último acceso	"Hace N días"	Rojo si > 15 días
Churn Score	Badge con porcentaje	Solo visible con permiso
Acciones	Menú contextual	
Acciones por fila (menú contextual):

Ver perfil completo
Registrar pago / renovar membresía
Enviar mensaje (futuro: push notification)
Marcar como intervenido (churn)
Cancelar membresía
Paginación: 25 filas por página. Ordenable por cualquier columna.

Página AD-04 — Staff Management (/dashboard/admin/staff)
Objetivo: Gestión completa del equipo de trabajo del gimnasio.

Permisos requeridos: gym.staff.ver para ver, gym.staff.gestionar para acciones

Tabs de la página:

Tab 1 — Trabajadores Activos:

Tabla principal:

Columna	Dato
Trabajador	Avatar + Nombre + Email
Rol RBAC	Badge con nombre del rol y jerarquía
Estado	Activo / Suspendido / Por expirar

Formulario de generación de código:

Selector de rol (desplegable con los 7 roles del sistema + custom futuros)

Descripción opcional ("Para el nuevo recepcionista del turno tarde")

El código grande y visible (ej: GYM-4F2K-8X9M)
QR del código
Botón "Copiar enlace de registro"
Botón "Compartir por WhatsApp"
Alerta de límite de licencias si aplica (max_licenses)
Tab 3 — Historial de Códigos:

Tabla de todos los códigos generados:

Columna	Dato
Código	Texto parcialmente oculto (últimos 4 dígitos visibles)
Rol asignado	Badge del rol
Estado	Activo / Usado / Expirado / Revocado
Creado	Fecha + por quién
Usado	Fecha + nombre del trabajador que lo usó (si fue usado)
Vence/Venció	Fecha
Usos	X de Y
Acciones:

Ver QR del código (si está activo)
Revocar código activo
Ver quién usó el código (link al perfil del trabajador)
KPIs en la parte superior de la Tab:

Trabajadores activos / Licencias disponibles (visual: "6 de 10 licencias usadas")
Códigos activos sin usar
Tasa de conversión del último mes (códigos generados vs usados)

6.3 Reglas del middleware de rutas
El middleware verifica en orden:

¿Existe una sesión válida de Supabase? Si no → /login
¿El string gym.usuarios.rol tiene una ruta asignada en role_dashboard_map? Si no → /login con error
¿La ruta solicitada está en ROUTE_ALLOWED_ROLES para el rol del usuario? Si no → redirigir al dashboard propio
Para rutas críticas (staff, auditoría, configuración financiera): verificar adicionalmente fn_has_permission() en el servidor
