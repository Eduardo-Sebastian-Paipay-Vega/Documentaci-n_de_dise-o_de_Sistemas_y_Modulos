Pregunta de arquitectura — ¿Roles rígidos vs. permisos modulares?

Análisis:

Los roles rígidos actuales (gerente, recepcionista, etc.) funcionan bien para el 80% de los casos. Sin embargo, existen escenarios reales que rompen el modelo:

Un recepcionista de confianza que también maneja reportes
Un entrenador que también cobra en ausencia del recepcionista
Un gerente al que el dueño quiere restringir acceso a datos financieros
Recomendación para Fase B (no ahora):

Mantener los roles como "plantillas de permisos" (sigue siendo conveniente para alta masiva de staff). Añadir una capa de "overrides" por usuario individual. Esto da flexibilidad sin complejidad de administración total.

Arquitectura objetivo:


Rol → define permisos base
Usuario tiene Rol
+ Usuario puede tener overrides positivos (+ver_reportes)
+ Usuario puede tener overrides negativos (-procesar_pagos)
= Permiso efectivo = base_rol + overrides
Esto se implementa con una tabla user_permission_overrides adicional, sin tocar el RBAC actual.

FASE 6 — ANÁLISIS DEL MODELO RBAC
6.1 Estado Actual
El sistema implementa Role-Based Access Control en dos capas:

Capa 1: Application Layer (Next.js middleware)

Basada en la cookie gymsos_rol
Controla redirecciones y visibilidad de rutas
Problema: cookie legible por JavaScript → riesgo XSS e impersonation
Capa 2: Database Layer (Supabase RLS)

Basada en auth.uid() y claims del JWT
Row-Level Security por id_gimnasio
Correcto: esta es la línea de defensa real
El "sistema dual" identificado en la documentación se refiere a que el rol vive tanto en la cookie como en la tabla usuarios. Actualmente esto crea potencial inconsistencia si alguien manipula la cookie (aunque la DB no dejará pasar la operación).

6.2 ¿Debe mantenerse el modelo actual?
Sí, con una corrección crítica.

El modelo RBAC actual es conceptualmente correcto y está bien diseñado para el tamaño actual del sistema. Lo que debe cambiar:

Corrección obligatoria (seguridad):
Mover el rol del usuario de la cookie JavaScript al JWT de Supabase como app_metadata.role. Esto hace que:

El rol viaja en el token (firmado, no manipulable)
El middleware de Next.js lo lee del JWT, no de una cookie editable
La DB RLS también puede leer del JWT directamente
Se elimina la dualidad
Esta es la única corrección de seguridad crítica en RBAC.

6.3 ¿Debe eliminarse el sistema dual?
Sí, pero de forma gradual:

Fase inmediata: Migrar gymsos_rol cookie → JWT claim app_metadata.role

Fase B (6-12 meses): Añadir tabla user_permission_overrides para soporte de permisos granulares sin eliminar el modelo de roles base

Fase C (12-18 meses): Evaluuar si la escala (~500 gyms, 50K staff) justifica un sistema de permisos completamente modular (tipo Notion, con "workspaces" y "permission sets" configurables por gym owner)

6.4 ¿Cómo debe evolucionar?
Evolución en 3 horizontes:

Horizonte 1 (ahora) — Consolidar:

Corregir cookie → JWT
Añadir rol supervisor entre gerente y recepcionista
Unificar miembro y cliente en un solo rol con flags de nivel
Horizonte 2 (Fase B) — Flexibilizar:

user_permission_overrides por usuario
Permitir al gerente ajustar permisos de su staff sin cambiar el rol
Logs de todos los cambios de permisos en audit_logs
Horizonte 3 (Fase C) — Escalar:

RBAC configurable por gym (el dueño define sus propios roles)
Permission sets predefinidos que el gym puede asignar
API de permisos para integraciones de terceros

FASE 9 — DECISIONES ARQUITECTÓNICAS PENDIENTES
Estas decisiones deben aprobarse antes de programar cualquier feature de Fase B en adelante.

DA-01: ¿Crear el rol supervisor?
Contexto: Actualmente el gerente tiene acceso total. No hay nivel intermedio. En gimnasios reales, existe un "encargado de turno" que tiene más permisos que el recepcionista pero no puede tocar la configuración financiera.

Opción	Ventaja	Desventaja
A) Crear rol supervisor separado	Jerarquía real. Menos sobre-permisionamiento	Requiere nuevo dashboard
B) Mantener roles actuales + overrides	Menor cambio. Flexible caso a caso	Más complejo de administrar
C) No hacer nada	Cero esfuerzo	El gerente sigue siendo sobre-permisionado para delegación
Recomendación: Opción A. Un gym con más de 3 empleados necesita este rol. El costo de implementación es bajo (reutilizar dashboard de gerente con módulos ocultados).

DA-02: ¿Unificar miembro y cliente?
Contexto: Hoy son indistinguibles funcionalmente. Dos dashboards idénticos, dos entradas en roles, duplicación de código.

Opción	Ventaja	Desventaja
A) Unificar en miembro con campo nivel (básico/premium)	DRY, mantenible	Requiere migración de BD
B) Mantener separados y diferenciar realmente	Experiencias genuinamente distintas	Más trabajo de diseño y desarrollo
C) Eliminar cliente, todos son miembro con plan	Más simple posible	Pierde segmentación de negocio
Recomendación: Opción B. La diferenciación entre miembro estándar y cliente premium es una ventaja de negocio real si se implementa correctamente (ver 5.7). Vale el esfuerzo de diseñarla bien.

DA-03: ¿Dashboards propios para cada rol o sistema de componentes compartidos?
Contexto: Actualmente cada rol tiene su propia ruta de dashboard con componentes independientes. Esto genera duplicación (ejemplo: el widget de "últimos accesos" aparece en gerente y recepcionista de forma distinta).

Opción	Ventaja	Desventaja
A) Dashboards independientes por rol (actual)	Cada experiencia es perfecta para su rol	Duplicación. Difícil de mantener con 7 roles
B) Dashboard unificado con widgets configurables por rol	Un solo sistema. Fácil añadir roles	Complejidad inicial. Risk de "hacer todo para todos"
C) Hybrid: shell compartido + secciones por rol	Balance entre ambos	Disciplina de diseño requerida
Recomendación: Opción C. Un sistema de layout compartido con "bloques de contenido" que se activan según permisos. Similar al modelo de Notion/Linear donde el sidebar y la topbar son universales pero el contenido central es contextual al rol.

DA-04: ¿Revocación lógica o física de staff?
Contexto: Cuando un empleado deja el gym, ¿sus datos se eliminan o se marcan como inactivos?

Opción	Ventaja	Desventaja
A) Lógica (soft delete: is_deleted = true)	Preserva historial. Reversible. Audit trail intacto	BD crece. Queries más complejas
B) Física (DELETE)	BD limpia	Pierde historial. Irreversible. Rompe FK de registros históricos
C) Archivado (mover a tabla usuarios_archivados)	BD principal limpia + historial preservado	Más complejo. Dos tablas para gestionar
Recomendación: Opción A (lógica) para toda la Fase A y B. Si la BD crece demasiado (>100K usuarios en un gym), evaluar Opción C en Fase E.

DA-05: ¿Cómo se monetiza GYMsos? ¿Afecta el diseño actual?
Contexto: El modelo de negocio en FASE_4 define pricing por gym. Esto implica que eventualmente GYMsos tendrá un "super admin" que gestiona múltiples gyms como clientes. Actualmente el sistema solo tiene el rol admin que es super pero no está diseñado para ser multi-gym desde una interfaz de gestión.

Opción	Ventaja	Desventaja

B) Gestionar gyms directamente en BD (sin UI)	Cero esfuerzo ahora	No escalable. Solo el dev puede agregar gyms
C) Añadir /admin/gyms como ruta protegida	UI simple pero efectiva	Deuda técnica si no se diseña bien

DA-06: ¿Stripe ahora o después?
Contexto: Los pagos son manuales. Stripe no está integrado pero el campo de negocio lo requiere.

Opción	Ventaja	Desventaja

B) Integrar en Fase B-C cuando el core sea estable	Enfocarse en operación primero	Más tiempo sin pagos digitales
