## 2. MODELO IAM — OBJETOS DEL PRIMER PISO

Todos los objetos siguientes ya existen en la BD_Maestra y **NO deben ser modificados
destructivamente**. Este documento los describe para entender qué reutilizar.

### 2.1 Tabla `public.tenants` — La organización

| Columna | Tipo | Descripción |
|---------|------|-------------|
| `id` | `uuid PK` | Identificador único del tenant |
| `nombre` | `varchar(255)` | Razón social de la organización |
| `owner_id` | `uuid FK → profiles` | El **Dueño/Owner** del tenant |
| `plan_id` | `uuid FK → cat_planes` | Plan contratado (Básico, Estándar, Plus) |
| `is_active` | `boolean` | Si el tenant está activo o suspendido |
| `created_at` | `timestamptz` | Fecha de registro |

**Relación con stakeholders:**
```
public.tenants.owner_id → public.profiles.id  (el Owner es siempre 1 persona)
```

### 2.2 Tabla `public.profiles` — Todos los usuarios del sistema

| Columna | Tipo | Descripción |
|---------|------|-------------|
| `id` | `uuid PK` | Coincide con `auth.users.id` de Supabase |
| `tenant_id` | `uuid FK → tenants` | A qué tenant pertenece |
| `nombres` | `varchar(150)` | Nombres del usuario |
| `apellidos` | `varchar(150)` | Apellidos del usuario |
| `email` | `varchar(255)` | Email de acceso |
| `avatar_url` | `text` | Foto de perfil |
| `is_active` | `boolean` | Cuenta activa/desactivada |
| `created_at` | `timestamptz` | Fecha de creación de cuenta |

**Relación con stakeholders**: Todos los stakeholders internos del tenant tienen exactamente
UN registro en `profiles`. La diferenciación de rol se hace mediante la tabla `user_roles`.

### 2.3 Tabla `public.roles` — Catálogo de roles

| Columna | Tipo | Descripción |
|---------|------|-------------|
| `id` | `uuid PK` | ID del rol |
| `tenant_id` | `uuid FK → tenants` | Roles específicos de un tenant (NULL = rol global) |
| `nombre` | `varchar(100)` | Nombre del rol (ej: `admin`, `coordinador_ong`) |
| `codigo` | `varchar(50)` | Código único (ej: `ADMIN`, `COORD_ONG`) |
| `jerarquia` | `integer` | Nivel jerárquico (0=Owner, 10=Admin, 20=Coord, ...) |
| `descripcion` | `text` | Descripción del rol |

**Roles predefinidos del sistema (valores semilla en `cat_roles`):**

| Código | Nombre | Jerarquía | Stakeholder que representa |
|--------|--------|-----------|---------------------------|
| `OWNER` | Owner / Super Admin | 0 | Dueño del tenant |
| `ADMIN` | Administrador | 10 | Administrador general |
| `COORD_ONG` | Coordinador ONG | 20 | Supervisor de área ONG |
| `RRHH_MGR` | RRHH Manager | 30 | Operador Senior RRHH |
| `FINANCIERO` | Financiero | 40 | Operador Senior Finanzas |
| `MEDICO` | Médico Clínico | 50 | Operador clínico especializado |
| `DOCENTE` | Docente / Académico | 50 | Operador académico |
| `VOLUNTARIO` | Voluntario | 90 | Operador Estándar de campo |
| `AUDITOR` | Auditor | 99 | Solo lectura / auditor |

### 2.4 Tabla `public.user_roles` — Asignación de roles a usuarios

| Columna | Tipo | Descripción |
|---------|------|-------------|
| `id` | `uuid PK` | |
| `tenant_id` | `uuid FK → tenants` | Tenant al que aplica esta asignación |
| `user_id` | `uuid FK → profiles` | Usuario al que se asigna el rol |
| `role_id` | `uuid FK → roles` | Rol asignado |
| `sede_id` | `uuid FK → sedes` | (Opcional) Sede específica donde aplica el rol |
| `assigned_at` | `timestamptz` | Cuándo fue asignado |
| `assigned_by` | `uuid FK → profiles` | Quién hizo la asignación |
| `is_active` | `boolean` | Si la asignación está activa |

**Nota**: Un usuario PUEDE tener múltiples roles. La jerarquía efectiva se calcula tomando
el rol de menor valor numérico (mayor privilegio).

### 2.5 Tabla `ace.role_module_access` — Control visual de módulos por rol

Controla qué módulos son visibles y accesibles para cada combinación tenant + rol:

| Columna | Tipo | Descripción |
|---------|------|-------------|
| `tenant_id` | `uuid` | Tenant al que aplica |
| `role_id` | `uuid FK → roles` | Rol |
| `module_code` | `varchar(50)` | Código del módulo (ej: `MOD_FINANZAS`) |
| `can_read` | `boolean` | Puede ver el módulo |
| `can_write` | `boolean` | Puede crear/editar |
| `can_delete` | `boolean` | Puede eliminar |
| `can_approve` | `boolean` | Puede aprobar solicitudes del módulo |

### 2.6 Tabla `public.plan_entitlements` — Módulos habilitados por plan

Controla qué módulos están disponibles según el plan contratado por el tenant:

| Columna | Tipo | Descripción |
|---------|------|-------------|
| `plan_id` | `uuid FK → cat_planes` | Plan (Básico, Estándar, Plus) |
| `module_code` | `varchar(50)` | Módulo habilitado en ese plan |
| `max_users` | `integer` | Límite de usuarios (NULL = ilimitado) |
| `max_storage_gb` | `numeric` | Límite de almacenamiento |

## 4. FLUJO DE RESOLUCIÓN DE ACCESO (cómo el sistema decide qué puede ver un usuario)

```
USUARIO HACE REQUEST AL SISTEMA
         │
         ▼
1. auth.uid() → identifica al usuario autenticado (Supabase Auth)
         │
         ▼
2. fn_current_tenant_id() → determina el tenant activo de la sesión
         │
         ▼
3. RLS de la tabla consultada verifica:
   WHERE tenant_id = fn_current_tenant_id()
         │
         ▼
4. ace.role_module_access verifica:
   ¿El rol del usuario tiene can_read = true para este módulo?
         │
         ▼
5. plan_entitlements verifica:
   ¿El plan del tenant incluye este módulo?
         │
         ▼
6. Si pasa los 3 filtros → datos visibles
   Si falla cualquiera → acceso denegado (sin mensaje de error descriptivo)
```

## 5. EXTENSIONES DEL SEGUNDO PISO — GAPS IDENTIFICADOS

Las siguientes tablas/objetos NO existen en el primer piso y pueden ser necesarios para
completar el modelo de roles según lo definido en Fase 4 §4.2.

### 5.1 Tabla nueva: `public.tenant_custom_roles`

**Propósito**: Permitir que los tenants en Plan Estándar y Plus creen roles personalizados
sin modificar la tabla global `public.roles`.

```sql
-- RF-ACE-001 · CU-CONFIG-005
-- Módulo: Configuración / IAM | Plan: Estándar, Plus | Tipo: CREATE TABLE
-- Extiende: public.roles (sin modificarla)

CREATE TABLE IF NOT EXISTS public.tenant_custom_roles (
    id              uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       uuid        NOT NULL REFERENCES public.tenants(id) ON DELETE CASCADE,
    nombre          varchar(100) NOT NULL,
    codigo          varchar(50)  NOT NULL,
    jerarquia       integer      NOT NULL CHECK (jerarquia BETWEEN 1 AND 98),
                    -- 0 = OWNER (no personalizable), 99 = AUDITOR (no personalizable)
    descripcion     text,
    base_role_id    uuid         REFERENCES public.roles(id),
                    -- Rol base del que hereda permisos (opcional)
    is_active       boolean      NOT NULL DEFAULT true,
    created_at      timestamptz  NOT NULL DEFAULT now(),
    updated_at      timestamptz  NOT NULL DEFAULT now(),
    created_by      uuid         REFERENCES public.profiles(id),

    UNIQUE (tenant_id, codigo)
);

-- RLS
ALTER TABLE public.tenant_custom_roles ENABLE ROW LEVEL SECURITY;

CREATE POLICY "tenant_custom_roles_tenant_isolation"
    ON public.tenant_custom_roles
    USING (tenant_id = fn_current_tenant_id());

-- Trigger de updated_at
CREATE TRIGGER tr_tenant_custom_roles_updated_at
    BEFORE UPDATE ON public.tenant_custom_roles
    FOR EACH ROW EXECUTE FUNCTION fn_set_updated_at();

-- Índice
CREATE INDEX IF NOT EXISTS idx_tenant_custom_roles_tenant
    ON public.tenant_custom_roles (tenant_id);
```

### 5.2 Columna adicional en `public.plan_entitlements`: `min_role_hierarchy`

**Propósito**: Bloquear ciertas funcionalidades a roles de bajo privilegio dentro de un
mismo plan (ej: en Plan Estándar, solo Admin y Supervisor pueden exportar reportes).

```sql
-- RF-PLAN-002 · CU-CONFIG-006
-- Módulo: Billing / Plan | Plan: Todos | Tipo: ALTER TABLE (aditivo)
-- Extiende: public.plan_entitlements sin modificar columnas existentes

ALTER TABLE public.plan_entitlements
    ADD COLUMN IF NOT EXISTS min_role_hierarchy integer NOT NULL DEFAULT 99;
    -- Valor por defecto 99: cualquier rol puede acceder (más permisivo)
    -- Si se establece en 10: solo Admin o superior puede acceder a esa función en ese plan

COMMENT ON COLUMN public.plan_entitlements.min_role_hierarchy IS
    'Jerarquía mínima requerida para acceder a este módulo en este plan.
     0=solo Owner, 10=Admin+, 20=Coordinator+, 99=todos.
     Implementa la tabla 4.2.7 del Plan de Negocio.';
```

### 5.3 Vista: `vw_user_effective_access`

**Propósito**: Vista que combina `user_roles` + `ace.role_module_access` + `plan_entitlements`
para responder de forma eficiente: "¿Qué puede ver/hacer este usuario en este módulo?"

```sql
-- RF-ACE-003 · CU-IAM-007
-- Módulo: ACE / IAM | Plan: Todos | Tipo: CREATE VIEW
-- Lee: user_roles, roles, ace.role_module_access, plan_entitlements, tenants

CREATE OR REPLACE VIEW public.vw_user_effective_access AS
SELECT
    ur.user_id,
    ur.tenant_id,
    r.codigo        AS role_codigo,
    r.jerarquia     AS role_jerarquia,
    rma.module_code,
    rma.can_read,
    rma.can_write,
    rma.can_delete,
    rma.can_approve,
    pe.max_users,
    pe.max_storage_gb,
    pe.min_role_hierarchy,
    -- ¿El usuario tiene suficiente jerarquía para este módulo en este plan?
    (r.jerarquia <= pe.min_role_hierarchy) AS has_plan_access
FROM public.user_roles ur
    JOIN public.roles r           ON r.id = ur.role_id AND ur.is_active = true
    JOIN ace.role_module_access rma ON rma.role_id = r.id AND rma.tenant_id = ur.tenant_id
    JOIN public.tenants t          ON t.id = ur.tenant_id
    JOIN public.plan_entitlements pe ON pe.plan_id = t.plan_id
                                    AND pe.module_code = rma.module_code
WHERE ur.is_active = true;

COMMENT ON VIEW public.vw_user_effective_access IS
    'Vista consolidada de acceso efectivo por usuario.
     Combina roles asignados, permisos de módulo y entitlements del plan.
     Usar para decisiones de autorización en la capa de aplicación.';
```
